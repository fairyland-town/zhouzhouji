## 一、改了什么

**账户之间的转账，一条都不进记账总账。**

### 为什么

钱只是在自己名下的两张卡之间挪，**总资产分文未变**。
那笔钱**首次充值进来**时记账页已经算过一次收入了，转账再算一次就是同一笔钱算两遍 ——
跟 v1.9.0 要消灭的「账户消费镜像」是同一类错误。

### 判据

账户流水的 `linkedAccountId` —— **只有 `transfer()` 会写它**。
外部充值（`recharge` → `addEntry`）和每月扣款（`runDueRecurring`）都不写。

```js
// account_service.js flowToLedger()
if (e.kind !== ACCOUNT_FLOW.IN) return null;    // v1.9.0：只有充值进总账
if (e.linkedAccountId != null) return null;     // v1.13.7：转账不进总账
```

⚠️ `transfer()` 里那行 `_mirrorToLedger(to, inEntry)` **保留** ——
它现在必然返回 null，留着是为了让「所有镜像都走同一个门」。

### 🔴 旧数据也要清

v1.13.5 加「关联账户 = 转账」时，转入侧还是照充值的老路子镜像进了总账。
**只拦新的不够** —— 已入库的镜像会把收入总额一直顶高，用户自己翻账单看不出哪笔是错的。

新增 `AccountService.purgeTransferLedgerMirrors()`：
- kv 标记 `ledger_transfer_mirror_purged_v1137`，只跑一次；
- 在 `ledger_view.js` / `account_view.js` 各调一次（与 `purgeAcctLedgerMirrors` 并列）；
- 判定链路：记账镜像的 `accountId` + `accountEntryId` → 回查账户流水有没有 `linkedAccountId`。

⚠️ **不能只看 `category === 'acct_in'`** —— 外部充值镜像也是这个分类，那是用户**要**的。
⚠️ **只删记账侧，绝不碰账户流水** —— 那是余额的事实依据。
   别走 `unlinkLedgerEverywhere`（它的语义是「撤挂账」，会把账户流水一起删掉）。

## 七、顺手挖出并修掉：备份导入漏了转账指认的重映射（同日）

「继续」时我做了一轮「还有没有同类双计/静默错账」的排查，
`grep totalIn` 全 `web/` 只有那 4 个落点，已全部处理；于是转去看**备份导入**这条链，
发现一个**同类缺陷**（静默留半截账），一并修了。

### 病根

`database_service.importJSON()` 会**重新分配所有账户的整数自增 id**
（`_add` 内部 `delete rec.id`）。第 4 步专门给记账流水的 `accountId` 做了重映射，
但**账户流水里的 `linkedAccountId`（存的是对方账户的整数 id）没有重映射**。

后果不是报错，是**静默留半截账**：`AccountService.removeEntry()` 靠这个字段
找对方那条流水一起撤，找不到就只删一半 —— 用户在 A 看到 +200，
B 那边却没有对应的 −200，**两边余额各自看着都「算得通」**。

### 先写探针验证，再动手

没有直接信「读代码的怀疑」，写了个一次性探针（用完已删）跑真机：

```
idsBefore:  { 零钱: 1, 饭卡: 2 }
idsAfter:   { 占位账户: 3, 零钱: 4, 饭卡: 5 }     ← 合并导入后 id 偏移
linkedAccountIdBefore: 1
linkedAccountIdAfter:  1        ← 没重映射
peerExistsAfter:       false    ← 悬空
peerRemovedOnDelete:   false    ← 🔴 删一半，另一半没跟着撤
```

### 修法

`importJSON()` 第 3 步加**第二遍**（`acctIdMap` 要等所有账户插完才完整）：

```js
for (const { newId, entries } of addedAccounts) {
  const fixed = entries.map((e) => {
    if (!e || e.linkedAccountId == null) return e;
    const mapped = acctIdMap.get(Number(e.linkedAccountId));
    if (mapped == null || mapped === Number(e.linkedAccountId)) return e;
    return { ...e, linkedAccountId: mapped };
  });
  ...
}
```

🔴 **找不到对方时「保持原样」而不是清空** —— 和第 4 步「不留悬空指针」**故意相反**：
这个字段同时是 `isTransferLeg()` 的唯一判据，清掉它会让转账被当成外部充值
**重新算进累计收入**，正好又变成双计。留着旧 id 只是找不到对方，但「这是转账」保住了。

修完探针复跑：`linkedAccountIdAfter: 4` / `peerExistsAfter: true` / **`peerRemovedOnDelete: true`** ✓

### 回归

`verify:backup` 新增**第 2.5 节**（65 → **69 项**）：

```
✓ 转账转入侧的 linkedAccountId 指向真实存在的账户
✓ 而且指向的是**正确**的那个账户（不是随便一个）
✓ linkedEntryId 未受影响（流水 id 是字符串，原样保留）
✓ 🔴 删掉转账的一半，另一半跟着撤（不留半截账）
```

⚠️ 必须用 **`merge: true`** 测：替换模式自增从头发号、旧 id 恰好还对得上，**测不出来**。
这条坑已写进技能 `regression-assertion-discipline` 的新 Rule 8。

**负向验证**：把第二遍 `continue` 掉 → **3 条红**（含行为那条）。
顺带印证了「指向随便一条」的风险：偏移后旧 id `3` 落在**无关的「占位账户」**上，
所以「能解析到某个账户」这条断言是**必需的**，光看「不是 null」会漏。

全量：**11 套件全绿 / E2E 235**；13 个 npm 回归脚本 **690 项全绿**
（backup 69 / transfer 90 / assets 80 / ledgeracct 118 / ledgerlist 85 / icons 42 /
ledgerform 41 / glass 39 / skip 29 / gestures 28 / pwa 25 / nav 25 / week 19）。

## 八、第三处同类问题：`dailyBurn()` 把转账当消费（用户拍板「改」，已改）

排查同类问题时找到第三处：`models/account.js` 的 **`dailyBurn()`** 用 `this.totalOut`（含转账转出），
区间也取到最早那笔 OUT。

实测（真跑模型，不是读代码推的）：

```
零钱：期初 500，今天转出 400 给饭卡
余额 100 / totalOut 400 / totalOutExternal 0
→ 日均消耗 400 → 还能用 0 天     🔴 卡里明明还有 100
```

而且 `daysLeft() <= 7` 会点亮警告色 → **纯转账触发「余额告急」假警报**。

### 先问了一句，用户说「改」

和前面两条不同：这条是**显示用的估算**，库里没写错任何数据；
改完的直接效果是那行 `日均 … · 还能用 …` **整条消失**（`daysLeft()` 为 null 时 UI 不渲染），
属于用户看得见的行为变化 —— 所以停下来问了，用户回「改」。

### 改法

```js
const outs = this.entries.filter((e) => e.kind === ACCOUNT_FLOW.OUT && !isTransferLeg(e));
...
return round2(this.totalOutExternal / spanDays);
```

🔴 **求和与区间必须用同一套过滤。** 只换求和、`outs` 里还留着转账的话，
会算出「20 / 31 ≈ 0.65」这种**被拉长的分母** —— 数字看着更温和，其实是错的。

### 顺带纠正一条假注释

原注释写「最多看最近 90 天」，但代码里**从来没有这个上限**（`outs[0].date` 一直取到最早那笔）。
已把注释改成与实现一致。**要不要真加 90 天上限是另一个决定**，没顺手加
（会让老账户的日均变大、可用天数变短）。

## 十、核对签名密钥备份（「继续」时的顺手一件）

悬着的重大风险是「钥匙丢了就再也无法覆盖安装」。这次**实际去核对了**，
而不是只看「文件在不在」——**存在 ≠ 能用**。

| 核对项 | 方法 | 结果 |
|---|---|---|
| 备份里的密钥库**就是**签这个包的那把 | `sha256sum` 比对两份 `zhouzhouji-release.keystore` | 字节完全一致（`2916b16188d5e44971732e4c…`） |
| 说明文件记的指纹 = **实际签名**指纹 | `keytool -printcert -jarfile dist/周周记-v1.13.7.apk` | `A1:0D:B8:D9…FA:8A:A6`，与 `密钥信息-必读.txt` 一致 |
| 三个必需信息都在 | 看 `密钥信息-必读.txt` | 密钥库密码 / 密钥别名 / 别名密码 全有 |

**结论：本机这份是完好的。唯一没做的是「拷到机器外面」**（网盘 / U 盘 / 密码管理器）
—— 硬盘挂了本地备份会一起没。已写进 `README.md` 和 `06_安卓安装与部署.md`。

### 踩的坑

- `apksigner.bat` 走 `cmd //c` + 中文路径**一个字节都打不出来**（静默无输出）。
  换 `keytool -printcert -jarfile` 一次就出。
- 🔴 `keytool` 传路径**必须用 Windows 形式**。传 `/tmp/zzj.apk` 报
  `NoSuchFileException: \tmp\zzj.apk` —— Git Bash 的 `/tmp` 不是 Java 眼里的路径。
- `apksigner.bat` 的实际位置是 `/d/android-toolchain/android-sdk/build-tools/35.0.0/`，
  **不在** `%LOCALAPPDATA%\Android\Sdk` 下（那是另一个工具链）。
