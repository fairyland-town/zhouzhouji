中间用户问了一句 **「为什么安装包这么大啊，不是没什么应用功能吗，其他类似软件才几十mb」** ——
这是把**开发工具链**和**安装包**搞混了，用两张图讲清楚了：

- 对比：Flutter 通用包约 40 MB、React Native 约 25 MB —— 他们要把引擎打进 APK。

### 🔴 四个坑（都踩了，已写进 `topics/备份与安卓.md`）

1. **项目路径含中文** → AGP 直接拒绝构建（`Your project path contains non-ASCII characters`）。
   修：`android/gradle.properties` 加 `android.overridePathCheck=true`
   + `org.gradle.jvmargs` 补 `-Dfile.encoding=UTF-8`。

2. **`npx cap sync android` 会冲掉 Gradle 仓库镜像补丁** ——
   它会**重新生成** `android/capacitor-cordova-android-plugins/build.gradle`，
   把仓库地址变回不可达的 `google()`。
   修：写 `tools/patch_gradle_mirrors.mjs`（幂等）并挂在 `android:sync` 后面自动跑。
   **教训：并发/生成式构建里，只改文件不写脚本是没用的 —— sync 一次就白改。**

3. **`sdkmanager` 装 `platforms;android-36` 会失败** ——
   内置解压器在 Windows 上处理这个包出错，装完目录里**只有一个空的 `.installer`**，
   连 `source.properties` 都没有。
   修：直接下 `platform-36_r02.zip` 自己 `unzip`。
   ⚠️ **必须 r02** —— AGP 8.13 要的就是 revision 2，装 r01 会被判「缺少组件」。
   （`build-tools` / `platform-tools` 用 sdkmanager 装是正常的，只有 platform 有这个毛病。）

4. **Adoptium 官方 API 只有 23 KB/s**（195 MB 要 2.5 小时）。
   换清华镜像 → **13 MB/s，13 秒下完**。Gradle 换腾讯云镜像（已写进
   `gradle-wrapper.properties`）。`dl.google.com` 本身正常（约 9 MB/s），不用换。

### 顺带做的两件事

- **版本号自动同步**：`android/app/build.gradle` 顶部用 `JsonSlurper` 读
  `package.json` 的 `version`，`versionCode` 按 `major*10000+minor*100+patch` 折算。
  改前 APK 显示 `versionName=1.0`（Capacitor 默认值），与网页端 v1.11.0 对不上。
  **现在改 `package.json` 就够了，不用手改 gradle。**
- **`tools/patch_gradle_mirrors.mjs`** + `npm run android:mirrors` 脚本。

### 签名答疑

查了 debug keystore 真实值：
别名 `androiddebugkey`、主体 `CN=Android Debug, O=Android, C=US`、
口令 `android`/`android`（**公开**）、SHA-1 `4D:EE:EC:09:…:5E:17`、有效期至 2056-09-09。

⚠️ **keytool 用 Git-Bash 的 `$HOME` 路径会报「密钥库文件不存在」** ——

（`-keystore 'C:\Users\27693\.android\debug.keystore'`）。

讲了四层：签名是**身份绑定**不是加密 → 换密钥就覆盖不了已装应用
（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）→ 商店拒收 debug 证书

### ⚠️ 纠正了一个自己说错的数字

实测拆包（4.71 MB，用 Python 读 `zipfile` 的 `compress_size`）：

| 组成 | 压缩后 | 占比 |
|---|---|---|
| dex 字节码（Capacitor 运行时 + 插件） | 3.33 MB | 70.8% |
| **web 资源（应用本体）** | **0.74 MB** | 15.6% |
| res 资源 | 0.34 MB | 7.1% |
| resources.arsc | 0.28 MB | 5.9% |
| 其它 / META-INF | 0.03 MB | 0.6% |

- `android/app/build.gradle` 的 release 是 **`minifyEnabled false`**（Capacitor 默认），
  **出正式包体积基本不变** —— 做正式签名是为了**身份**，不是为了瘦身。
- **教训：给用户的数字必须实测。** 上一条的 2–3 MB 是编的。

### ④ 图片识别在手机上完全不能用 ⏸ 待决策

## 一、记录页左右滑动翻板块

难点**不是「怎么翻」，而是「怎么不误伤纵向滚动」** —— 记录页全是长列表，
无脑 `preventDefault()` 页面就滑不动了。解法是**先定轴，再拦截**：

- 位移 < `AXIS_LOCK`(9px) 时**直接 return，不拦**；
- 超过后比 `|dx|`/`|dy|`：纵向 → `tracking = false`，**整个手势交还浏览器**；
- 横向才 `preventDefault()` 接管，首尾用 `RUBBER`(0.34) 阻尼回弹。
- 翻页动画两段式（滑出 → 换内容 → 从另一侧滑入），
  中间**必须 `void bodyHost.offsetWidth` 强制重排**，
  否则两次样式变更被合并 → **跳变而不是滑动**。

> 🔴 记两条通用教训：
> ① **只有 touch 事件能 `preventDefault()`**（`pointermove` 不可取消），
>    「定轴后才拦」这套策略**只能用 touch 实现**。
> ② **`touch-action` 不继承** —— 只写在容器上，子元素照样会被横向拖动带歪。

## 二、侧滑返回：先读源码定位根因，再动手

读了 `@capacitor/app` 的 `AppPlugin.java:46-58` 才看清真相：

- JS **注册过** `backButton` → 原生把事件交给 JS，**自己什么都不做**；
- **没注册** → `canGoBack() ? webView.goBack() : (什么都不做)`，
  而「什么都不做」落到 Activity 默认行为 = **退出 App**。

本项目的导航栈是**内存里的 `ctx.stack`**（v1.3.0 起有意不用 history 路由），
所以 `canGoBack()` **恒为 false** → 第一次滑不做事、第二次滑退出。
用户描述的「滑两次直接退出软件」被源码完整解释了。

修法：零构建项目不能 `import` 插件的 npm JS，但注入的 `window.Capacitor` 有 `addListener`，
于是加 `native_bridge.onNativeEvent(plugin, event, handler)` 直接注册，
**不需要打包任何插件 JS**。注册后原生就完全不再自动退出。

`handleBack()` 四级阶梯：**① 关浮层 → ② 记录页退回第一个板块 → ③ 退一层路由 →
④ 两步退出**（2 秒窗口，第一次只 toast）。

顺带修了一个**同源的旧 bug**：`go()` 回到根路由时不清栈，导致
`week → add → confirm → week` 之后按返回会退回**已经提交过的确认页**。
另外把 6 个页面的返回按钮从 `ctx.go('week')` 改成 `ctx.back()` ——
前者是「跳回首页」，不是「返回」，语义是错的。

> 🔴 浮层栈的 `dismiss` **必须走各自的正常取消路径**，不能 `overlay.remove()`：
> 浮层背后通常有个 `await` 着的 Promise，直接摘 DOM 会让它**永不 resolve**，
> 调用方静默挂死 —— **不报错，只表现为「点了没反应」**。

## 三、账户资产板块

四个新模型（借入借出 / 报销 / 黄金 / 定期）**全部存已有的 `kv` 表**：

> 新建 store 要升 `DB_VERSION`、写迁移、改备份顺序、改清空分类 —— 四处联动只为存几个数组。
> `kv` 本来就在 `BACKUP_STORES` 里，白拿备份能力。代价是清空分类要显式列 `kvKeys`。

净资产口径（纯函数，`today` 外部注入）：

```js
totalAssets      = cashPositive + lentOut + pendingTotal + goldValue
totalLiabilities = cashNegative + borrowedIn
netWorth         = totalAssets - totalLiabilities
```

- **借入是负债、借出是资产**，不是「都是钱」；
- **定期不计入净资产** —— 那笔钱通常已躺在某个账户余额里，再加一次就是重复计算
  （用户要的「全局口径」正是为了避免这个）；
- 余额为负时按 `max(bal,0)`/`max(-bal,0)` 拆两侧，不出现负数资产。

UI：净资产大卡（含金额隐藏开关）、两排指标格、金价/定期卡、全局口径格、
按类型分组的分布（可折叠）、四类明细的管理弹层。`money()` 补了千分位
（注释里早写着 `¥1,234.50`，代码却输出 `¥1234.50`）。

# v1.13.1 —— 账户页视觉层级重排 + 重装找回数据

用户看过 v1.13.0 的账户页后提了两件事，并要求**先出图验收、别急着打包**：

## 一、发现「什么都一样大」的真正原因

一开始以为是「卡片尺寸雷同」，读完代码才看清根因：
**每个小格子有三行** —— 标签 / 数值 / 一行解释文字（「我欠别人的」「已拿回来的」…）。
三行撑出来的高度让**格子比净资产大卡还高**，整页自然没有层级。

所以用户的两条反馈**是同一个病**：删掉第三行，格子自然变矮，层级也就出来了。

改成三级：

| 层级 | 元素 | 做法 |
|---|---|---|
| 一级 | 净资产 | 字号 28→**34px**、weight 800、留白 14→18px、底色更实 |
| 二级 | 借入借出 / 黄金定期 | **只留两行**；逾期压成标签行右侧的小角标 `.acct-metric__flag` |
| 三级 | 账户概览 | **不再是格子**，改成「标签左 / 数值右」的紧凑列表 `.acct-ovlist` |

关键判断：**视觉层级要用字号和留白拉，不要靠加边框加底色** ——
加装饰只会让所有卡片更像。以及**同类信息堆成一排等大的格子 = 没有层级**，
次要信息改成列表就自然退到后面了。

删掉的解释文案：我欠别人的 / 别人欠我的 / 已拿回来的 / 垫了还没报的 /
持仓 N 笔 / 不计入净资产 / 点一下填金价 / 还没登记持仓 / 共 N 个账户 /
累计口径 · 全部账户 / 点分组收起 / 点卡片展开充值消费对账。
保留的是**状态**（N 笔逾期、即将到期金额、全部对得上），不是解释。

顺带删了两处死代码：`goldDepositCard` 里算好却从没用过的 `left`，
以及随之失效的 6 条 CSS 规则（`.acct-metric__sub` / `.acct-total__sub` /
`.acct-overview__hint` / `.acct-section-title__hint` / `.acct-metric--static` /
`.acct-grid--overview`）。

**层级用断言钉住**，不靠感觉（`verify_assets.mjs` 53 → 58 项）：
字号比 ≥1.8（实际 34 vs 17）、净资产卡高 ≥ 格子卡高（203 vs 164）、
每格 `children.length === 2`、外加一份**禁用词表**（出现即失败）。
原来的「借出不被借入的逾期带偏」是读 `sub` 文案的，文案删了之后
改成读 `.acct-metric__flag` 是否为空 —— **断言要跟着语义走，不要跟着文案走。**

## 二、用户追问：「为什么每次更新都必须卸载？数据不就没了？」

这是个好问题，而且**答案对我们有利**：不用，只有那一次。

- 需要卸载的**唯一原因**是当时手机上装的是 **debug 包**
  （`dist/debug历史/` 里的 v1.11.0-debug / v1.12.0-debug），
  而新包是 release 签名，两者密钥不同 → 系统认为不是同一个应用 → 拒绝覆盖。
- **从 v1.12.0 正式版起所有 release 包共用同一把钥匙**，
  所以之后每次更新都是**直接覆盖安装**（Android 显示「更新」），数据原样保留。
- 覆盖安装成立靠三件事同时满足：包名相同（`com.zhouzhouji.app`，没改过）、
  签名相同、`versionCode` 递增（`major*10000+minor*100+patch`，11300 → 11301）。

顺带把「卸载到底删什么」查清楚了：

| 位置 | 卸载后 |
|---|---|
| IndexedDB / localStorage | **删掉**（应用私有目录） |
| `Documents/周周记备份/` | **保留**（公共目录） |
| `ExternalStorage/…`、`Data/…` | 删掉（回退落点，活不过卸载） |

所以备份的落点很关键 —— 只有落在「文档」目录才扛得住卸载。
目录回退链的后两级都活不过卸载，设置页会把实际落点显示出来。

## 三、补上「重装后主动找回数据」（v1.13.1）

光解释「不用卸载」还不够 —— **万一真卸载了**（或换机、被系统清数据），
数据虽然还在「文档」目录里，却没人告诉用户。新增 `offerRestoreIfFresh()`：

- 本机第一次打开 + 数据库是空的 + 翻到上一份备份 → 弹窗问一句「要恢复吗」，
  确认后 `importJSON(json, {merge:false})` 整份还原。
- **「只问一次」的标记存 `localStorage`，不能存 `kv`** ——
  `kv` 会被「设置 → 清空数据」一起清掉，那样用户刚清完数据、
  下次启动又会被问「要不要恢复你刚删的东西」。
- **判空必须用新加的 `DatabaseService.isEmpty()`，不能用 `count()`** ——
  `count()` 只数 `events` 一张表，「只打过卡、没记过活动」会被误判成空库，
  然后把提示弹给一个正在用的人。这个坑很容易踩，已写进注释。
- 浏览器里第一行就 `return null`。

有数据不打扰 / 没文件不空提示 / 有备份就交出来 / 只问一次 / 标记位置 / 浏览器不检查）。
给 mock 补了 `readFile`，用 `window.__backupFile` 控制「手机里有没有那份备份」。

> 踩坑：`verify_backup.mjs` 的断言帮手是 `check(名, 布尔)` / `eq(名, 实际, 期望)`，
> **没有 `ok`**（那是 `verify_assets.mjs` 的）。我先按 `verify_assets` 的签名写了
> `check(名, 实际, 期望)`，结果 `null` 被当成 falsy → 前两条假失败。

# v1.13.1 补：修掉「设置页版本号硬编码」这个真 bug

继续收尾时顺手查了一下设置页，**发现一个真 bug**：

```js
// web/js/screens/settings_screen.js:13
const VERSION = 'v1.12.0';        // ← 硬编码，而 package.json 已经到 1.13.1
```

## 为什么这个 bug 特别要紧

用户这轮问的正是「**我怎么知道更新装上了没有**」。
设置 →「关于」里那行 `版本 vX.Y.Z` 就是他唯一能查的地方 ——
**而它显示的是 v1.12.0，不管实际装的是哪个版本。**
这不是「显示旧了」，是**它会让用户以为更新失败了**。

`android/app/build.gradle` 的注释里早就写着「package.json 是版本号唯一真源」，
安卓端的 `versionName`/`versionCode` 确实是读 `package.json` 的 ——
**只有网页端这一处漏了**，手写了一份。

## 修法：把版本号收敛成真正的单一来源

没有简单地把 `'v1.12.0'` 改成 `'v1.13.1'`（那只是把下一次漂移推迟），
而是让 `tools/build_pwa.mjs` 从 `package.json` **生成** `web/js/version.js`：

```js
// tools/build_pwa.mjs 新增第 ⓪ 步（在扫描静态资源之前写，
// 这样 version.js 才会被算进 PRECACHE 清单）
const versionJsBody = `export const APP_VERSION = '${pkg.version}';
export const APP_VERSION_TAG = '${version}';`;
```

设置页改成 `import { APP_VERSION_TAG } from '../version.js';`。
现在版本号的四个落点全部自动同步：

| 位置 | 用途 | 来源 |
|---|---|---|
| `package.json` | **唯一真源** | 手动改这一处 |
| `web/js/version.js` | 设置→关于 显示 | `build_pwa.mjs` 生成 |
| `web/sw.js` 的 `VERSION` | 缓存键 | `build_pwa.mjs` 生成 |
| 安卓 `versionName`/`versionCode` | 决定能否覆盖安装 | gradle 读 `package.json` |

`--check` 模式也会校验 `version.js`，所以 CI / `npm run pwa:check` 能拦住漂移。

## 断言 + 负向测试

`tools/verify_pwa.mjs` 21 → **23 项**，新增两条：
设置页 `[data-field="app-version"]` 的文本必须等于 `版本 v${package.json.version}`；
外加一条「元素确实存在」（否则取不到元素时会假失败）。

**做了负向测试**：把 `version.js` 改回 `v1.12.0` → 脚本报
`✗ 设置页显示的版本与 package.json 一致 （页面「版本 v1.12.0」/ package.json「v1.13.1」）`，
改回来后恢复绿。**绿的前提是它真的能红。**

> 顺带记一条通用教训：**凡是「同一个值在多个地方各写一份」的字段，
> 迟早会对不上，而且往往是在最要命的地方对不上**（这次是用户用来判断更新成败的那一行）。
> 发现这种字段，正确的做法是**收敛成单一来源 + 生成**，
> 而不是「把这一处也改对」—— 后者只是把漂移推迟到下一次。

# v1.13.2 —— 小格子再收紧 + 黄金撤出账户页

用户原文：

> 「借出借入，定期到期这些办款还是很大，再缩小，然后就是去掉金价板块」

追问后选定 **「删掉整个黄金（金价 + 总克重）」**。

## 一、真正的元凶是行高，不是 padding

v1.13.1 把每格从三行压到两行、padding 10px → 6px，用户仍说「还是很大」。
实测 56px，比我按 padding 估的 43px 高一大截。

**默认行高（≈1.6）才是这两行小字的主要高度来源。**

| 组成 | 原 | 只减 padding | 再钉行高 |
|---|---|---|---|
| 上下内边距 | 20px | 12px | 12px |
| 标签行 10.5px × 行高 | ≈16.8 | ≈16.8 | **13.1** |
| 间距 | 3px | 2px | 2px |
| 数值行 15px × 行高 | ≈24 | ≈24 | **18.8** |
| 上下边框 | 2px | 2px | 2px |
| **单格** | **≈66px** | **56px** | **48px** |

> 🔴 **通用教训：调小一个「两行小字」的卡片，先看行高，再看 padding。**
> 默认行高 1.6 意味着 15px 的字实际占 24px —— 字号的 1.6 倍。
> 只动 padding 顶多收 20%，钉住 `line-height: 1.25` 才能收住。
> 我在第一次估算时完全漏了这一项，`< 50px` 那条断言第一次就是红的（56px），
> 是它把真正的原因逼出来的。

## 二、删掉一个「入口」之前，先查它是不是唯一入口

黄金市值**仍然计入净资产**，但 `openGold()` 当时**只被那两格调用**。
直接删两格 = 用户改不了金价、删不掉持仓，而那个数一直在算。
**看不见、改不动、但一直在算的幽灵数字。**

修法：面板抽成 `web/js/screens/record/gold_sheet.js`
（`openGoldSheet({ onChange })`，不认任何页面），
入口挪到 **「设置 → 其他 → 黄金持仓」**（显示 `持仓 10 克 · 金价 ¥900.00/克`）。

> 🔴 **通用教训：删 UI 元素前，先 `grep` 这个元素的 onclick 指向的函数，
> 看它还有没有别的调用点。** 功能被删掉显示、但数据仍在参与计算时，
> 必须给它留一个入口，否则就是死路。

## 三、回归脚本自己的假阳性

给 `verify_assets.mjs` 加了「进设置页看黄金入口」这一步后，末行开始报红：
`Failed to load resource: net::ERR_CONNECTION_REFUSED`。

设置页会探测本机 OCR 服务 `http://127.0.0.1:8765/health`，测试机上没开，
浏览器必然抛这条。而老过滤条件 `!/OCR/.test(m.text())` **挡不住** ——
消息文本里既没有「OCR」也没有端口号。

修法：**按来源 URL 过滤，不按消息文本**。

```js
const isOcrProbe = (m) => {
  try { return /127\.0\.0\.1:8765/.test(m.location()?.url || ''); } catch { return false; }
};
```

**做了负向验证**：写探针打印 `m.location().url`，确认确实是
`http://127.0.0.1:8765/health` —— 证明过滤器**真的命中**，
而不是「错误恰好没发生」。不这么验一遍，就等于没验。

> 🔴 **通用教训：console 错误的来源要看 `m.location().url`，
> 不要只看 `m.text()`。** 资源加载失败的消息文本永远是同一句
> `Failed to load resource: net::ERR_XXX`，从文本里分不出是谁在报错。

# v1.13.3 —— 周历页「总是跳到周日」

用户原文：

> 「还有一个问题是，每次点击周历的时候，总是跳转到最后，周日，而不是具体的当天日期居中」

## 一、根因：`offsetTop` 量错了参照系

```js
body.scrollTop = Math.max(0, sec.offsetTop - 12);   // ❌
```

`offsetTop` 是**相对 offsetParent** 的距离。`.app-body` 与 `.screen` 都**没有 `position`**，
它们的 offsetParent 一路找到 `#app`（只有 `#app` 有 `position: relative`）。
所以量出来的是「相对整个应用顶部」的距离，比在滚动容器里的真实位置
**多出头部 + 筛选条 + 日期条那一整段** —— 实测 **205px**。

实测数据（430×900 视口，7 节各 238px）：

| | 值 |
|---|---|
| `sec.offsetParent` | `app` |
| `sec.offsetTop` | 463 |
| `body.offsetTop` | 205 |
| 今天在容器里的真实位置 | **258**（= 463 − 205） |
| 原代码设的 `scrollTop` | **451**（= 463 − 12） |
| 结果 `secTopInBody` | **−193px**（今天被滚到视口上方看不见） |

多滚 205px 的后果分两种：内容够长 → 停在**后一天**；内容不够长 →
`scrollTop` 被钳到最大值 → **直接落到周日**。用户撞上的是后者。

## 二、修法

不依赖 offsetParent，用 `getBoundingClientRect()` 相减再居中：

```js
const box = body.getBoundingClientRect();
const secBox = sec.getBoundingClientRect();
const topInBody = secBox.top - box.top + body.scrollTop;
const max = Math.max(0, body.scrollHeight - body.clientHeight);
const centered = topInBody - (body.clientHeight - secBox.height) / 2;
body.scrollTop = Math.max(0, Math.min(centered, max));
```

修完：`scrollTop` 451 → **30**，`secTopInBody` −193 → **228**（= (695−238)/2，正好居中）。

## 三、新建 `tools/verify_week_scroll.mjs`（19 项，`npm run verify:week`）

周历页以前**没有任何专项回归脚本**，所以这个 bug 才能一直活着。覆盖 5 个场景：

| 场景 | 断言 |
|---|---|
| A 内容远高于视口 | 今天那一节完整可见、没滚过头、**没有直接落到周日** |
| B 内容矮于视口 | 完整可见 + `scrollTop === 0`（不乱跳） |
| C 切到上一周 | 没有「今天」那一节 + **不自动滚动** |
| D 点「回到本周」 | 又回到今天居中 |
| E 点日期条 | 周四贴顶；**周日只能要求完整可见 + 已滚到底** |

> 🔴 断言的是**语义**（「今天那一节完整落在可视区内且尽量居中」），
> 不是「`scrollTop` 等于某个数」—— 后者一改布局就假红。

⚠️ **E 场景第一次写错了**：要求「点周日 → 周日贴顶」，红了（距顶部 367px）。
这不是 bug，是**物理事实** —— 周日是最后一节，要它贴顶就得滚过 `maxScroll`。
**断言必须服从物理约束**，改成「完整可见 + 已滚到底」。

## 四、负向测试

把实现临时还原成 `offsetTop` 版（用 `.debug/week_screen.bak` 备份 + 字符串替换），

## 做法

账户页那一节原来是静态标题 `账户明细` + 一摞账户大卡（默认全摊开）。
「资产分布」已经列过每个账户的名字 + 余额，再摊开一遍 = 同一批账户出现两次。
