## 问题 1：`promptDialog` 返回值二义性 → 已修

**根因**：`checkin_view.js` 的 `promptDialog` 里 `read()` 写的是
`input.value.trim() || null`，于是**留空确定**和**点取消**都 resolve `null`。
调用方写的 `if (due === null) return;`（本意是「取消就别记了」）
把老实留空跳过的用户一起挡在门外 —— 整笔账静默丢掉，连提示都没有。

**改法**：三态契约 —— `null` = 取消 / `''` = 明确留空（跳过）/ 其它 = 输入内容。
- 借出「约定哪天还」、定期「年利率」「到期日」、待办「截止日期」、账户「备注」：
  守卫从 `if (!x)` 改成 `if (x === null)`，留空真正变成「跳过」。
- **必填项改走 `required: true`**（弹窗自己就地提示），
  不再依赖调用方 `return` —— 那是「点了没反应」，用户更懵。
  涉及：金额 ×4、本金、新建账户名、重命名账户 / 打卡项 / 待办、垫付事由、
  克重、粘贴支付信息、新建打卡项。
- ⚠️ **数值型弹窗尤其危险**：留空 → `Number('')` = **0**。
  「设置当前余额 / 对账 / 金价 / 每月扣款 / 每月几号扣 / 期初余额」
  都因此加了 `required` —— 清空输入框会把余额或净资产**悄悄清零**，
  比直接报错可怕得多。

## 问题 2：日期多格式 → 已修

新增 `parseDateInput()`（`utils/date_utils.js`），放行
`2026-10-08` / `2026.3.8` / `2026.09.08` / `2026/3/8` / `2026-10-8` / `2026年3月8日`，
统一规范化成 `YYYY-MM-DD` 再落库。正则 `PATTERNS.DATE_INPUT`（**锚定首尾**）。

🔴 **必须回读校验**：正则只能保证「长得像日期」。`2026-02-31` 完全合规，
而 `new Date(2026, 1, 31)` 会被 JS **静默滚到 3 月 3 日** ——
存进去的是用户从没输入过的日期，事后查不出来源。
所以把构造出的 Date 反读年/月/日，三个都对上才算数。

接入点：借出到期日、定期到期日、待办截止日期。

## 追加硬化：全局静默失败兜底（同一 bug 家族）

用户报的「点了没反应」还有一条没被覆盖的路径：**异步点击处理器抛错**。
界面上大量 `onclick: async () => {...}`，里面某一步抛错又没被就地 catch 时，
浏览器只记一次 unhandledrejection，**界面什么都不发生**。项目此前**完全没有全局兜底**。

改了三处：

1. **`utils/dom.js` 的 `toast()` 加兜底文案**。
   调用方大量写 `toast(err.message, 'error')`，但 `err.message` 不保证是字符串：
   抛出的可能不是 Error（Capacitor 插件 / DOMException），`new Error()` 的 message
   默认还是空串。结果是**写着「undefined」的气泡**或**一个空白气泡** ——
   空白气泡看起来就是「点了没反应」。现在按 type 兜底（error→「操作失败，请重试」）。
2. **`main.js` 加 `unhandledrejection` 兜底**：转成人话 toast + 保留 console.error。
3. **`main.js` 加 `error` 兜底**：`if (e.target && e.target !== window) return;`
   过滤掉资源加载失败（那种消息永远是同一句，不该弹给用户）。

⚠️ 拒绝值**不能**直接 `String(reason)` 渲染 —— `Promise.reject({code:42})` 会得到
「操作失败：[object Object]」，`reject(null)` 会得到「操作失败：null」。
只有 `instanceof Error` 或字符串才配得上给用户看，其余走兜底文案。

### 🔴 踩坑记录：`page.evaluate` 抛的错会被脱敏，测不出兜底处理器

在 `verify_skip` 里用 `page.evaluate(() => { Promise.reject(...) })` 测兜底，
**一直测不出来**。查了三轮才定位：Chrome 把 `evaluate` 的代码当成**另一个源**，
事件里 `e.error === null`、`e.message === 'Script error.'` ——
我那个 `if (!e.error) return;` 直接把它挡了。

**是探针的假象，不是应用的 bug。** 正确做法是注入**同源内联脚本**再由它抛：

```js
await page.evaluate(() => {
  const s = document.createElement('script');   // 内联 = 同源
  s.textContent = `window.__boom = () => { setTimeout(() => { throw new Error('x'); }, 0); };`;
  document.head.appendChild(s);
});
await page.evaluate(() => window.__boom());
```

换成同源脚本后，两条路径立刻都通过（`unhandledrejection` 在 headless 下
**是正常派发的**，别误判成「headless 不支持」）。
这条已写进 skill 的踩坑清单。

验证：`verify:skip` 扩到 **29 项**（新增第 7 组 8 项），
含「同步抛错要弹提示」「异步拒绝要弹提示」「没有 message 也不能是空白气泡」
「不能出现 `[object Object]` / `undefined`」。
E2E 的「无控制台错误」断言**没变红** → 说明应用本身确实没有未捕获的拒绝，兜底不会误报。
