## 一、备份覆盖全部 7 张表（v1.11.0）

- `exportJSON()` 输出 **version 2**：`{ app, version: 2, exported_at, counts, events, checkins,
  checkin_logs, accounts, ledger, todos, kv }`。
  **events 走 `toJSON()`（不含 id）**，其余 6 表存**原始记录（含 id）** —— 它们的 id 是外键锚点。
- **导入顺序 = 依赖顺序**：`checkins → checkin_logs → accounts → ledger → todos → kv → events`
  （`BACKUP_STORES` 常量，别随意调）。
- 导入时**整数自增 id 全部重分配**并改写外键：`checkin_logs.checkin_id`、`ledger.accountId`、
  **`accounts.entries[].linkedAccountId`**（第三个 2026-09-24 才补上，见下面那条）。
  `accounts.entries[].id` 是全局唯一**字符串**（`e<base36时间><base36序号>`），**原样保留不重映射**。
- 🔴 **凡是存着「整数 id」的字段，导入后都必须重映射** —— 漏一个不会报错，
  只会**静默留下悬空指针**。踩过：`entries[].linkedAccountId` 存的是**对方账户的整数 id**，
  2026-09-24 才发现没重映射，后果是 `AccountService.removeEntry()` 找不到对方那条流水，
  **删掉转账的一半时另一半撤不掉 → 留下半截账**（A 有 +200、B 没有 −200，两边各自看着都算得通）。
  - 补映射必须**第二遍**做（`acctIdMap` 要等所有账户都插完才完整）。
  - ⚠️ 实测：**替换模式测不出来**（自增从头发号，旧 id 恰好还对得上）；
    **合并进非空库才会偏移**（旧 1/2 → 新 6/7），而那个旧 id 会落在**无关账户**上。
    回归断言必须用 `merge: true`，见 `verify:backup` 第 2.5 节。
  - 🔴 **找不到对方时「保持原样」而不是清空** —— 和第 4 步「不留悬空指针」**故意相反**：
    这个字段同时是 `isTransferLeg()` 的唯一判据，清掉它会让转账被当成外部充值
    **重新算进累计充值**，正好又变成双计。留着旧 id 只是找不到对方（本来就找不到），
    但「这是转账」这个事实保住了。
- **孤儿记录直接丢弃**：日志找不到对应 checkin → 丢；ledger 找不到 accountId → 丢。
- **两种导入模式**：合并（追加）/ 替换（先清库），由 `actionSheet` 让用户选，**不能默认替换**。
- **兼容三种历史格式**：v2 / v1（只含 events）/ 裸数组。
- 🔴 **`bulkAdd()` 必须用 `Event.fromRecord(item)`，不能用 `new Event(item)`** ——
  备份 JSON 是 **snake_case**（`start_time`），构造函数只认 **camelCase**（`startTime`），
  用后者会让 `startTime` 变空串 → `validate()` 失败 → **全部活动静默丢弃**。
  这个 bug 在 v1.10.0 及更早一直存在，靠 `verify_backup.mjs` 才挖出来。
- 回归：`node tools/verify_backup.mjs`（**69 项**，第 2.5 节守「合并导入后转账指认仍有效」，第 7 组守「浏览器端无回归」）。

## 三、无构建 → 只能用 `nativePromise`

- 项目**没有打包器**，所以 `import '@capacitor/filesystem'` 这种裸模块名**跑不起来**。
  正确做法：调 Capacitor 注入的底层通道
  `window.Capacitor.nativePromise(plugin, method, options)`
  （由 `native-bridge.js` 注入）。**不要把任何插件 JS 放进 `web/`** —— 会破坏零依赖原则。
- 封装在 `web/js/services/native_bridge.js`：`isNative()` / `callNative()` / `DIR` / `ENC`。
  **浏览器里全部 no-op**（`isNative()` 返回 false 就跳过），绝不能崩。
- 写文件参数：`{ path, data, directory, encoding: 'utf8', recursive: true }`。
  字符串 + `encoding:'utf8'` 走 TextEncoder，**不需要 base64**。
- **目录降级链**：`DOCUMENTS → EXTERNAL_STORAGE → DATA`（`DIR_CHAIN`），
  哪个能写用哪个，记在 `kv` 的 `backup_dir_used`。

### ✅ 原生调用链已逐环验证（2026-09-17）

`nativePromise` 是这套方案的命门 —— 名字写错就会**在真机上静默失败**（浏览器里全是 no-op，
本地测不出来）。已把整条链的每一环都对着源码/产物核过：

| 环节 | 证据 |
|---|---|
| `nativePromise` 存在 | `native-bridge.js:999` |

| 插件已打进 APK | `assets/capacitor.plugins.json` 含 `com.capacitorjs.plugins.filesystem.FilesystemPlugin` |
| 方法都存在 | `writeFile` / `readdir` / `deleteFile` / `getUri`（Kotlin）、`Share.share`（Java） |
| 运行时配置 | `assets/capacitor.config.json` → `androidScheme: https` |

### 🔴 四个坑（都踩过，别再踩）

1. **项目路径含中文 → AGP 直接拒绝构建**
   `D:\desktop\周历记` 触发
   `Your project path contains non-ASCII characters`。
   已在 `android/gradle.properties` 加 **`android.overridePathCheck=true`**，
   并把 `org.gradle.jvmargs` 加上 `-Dfile.encoding=UTF-8`。

2. **`npx cap sync android` 会冲掉 Gradle 仓库镜像补丁**
   它会**重新生成** `android/capacitor-cordova-android-plugins/build.gradle`，
   把替换过的仓库地址变回 `google()`（→ 不可达的 maven.google.com）。
   → 已写 `tools/patch_gradle_mirrors.mjs`（幂等），并挂在 `android:sync` 后面自动跑。
   **只改文件不写脚本是没用的，sync 一次就白改。**

3. **`sdkmanager` 装 `platforms;android-36` 会失败**
   报 `Warning: An error occurred while preparing SDK package Android SDK Platform 36:
   ...\optional\libbinder_ndk_cpp\android\binder_auto_utils.h`，
   装完 `platforms/android-36/` 里**只有一个空的 `.installer` 目录**，没有 `source.properties`。
   绕过：直接下 `https://dl.google.com/android/repository/platform-36_r02.zip` 自己 `unzip`。
   ⚠️ **必须是 r02（revision 2）** —— AGP 8.13 要的就是它，装 r01 会被判「缺少组件」。
   `build-tools` 和 `platform-tools` 用 sdkmanager 装是正常的，只有 platform 有这个毛病。

4. **Adoptium 官方 API 极慢**（实测 23 KB/s，195 MB 要 2.5 小时）。
   换清华镜像 `mirrors.tuna.tsinghua.edu.cn/Adoptium/...` → **13 MB/s，13 秒**。
   同理 Gradle 用 `mirrors.cloud.tencent.com/gradle/`（已写进 `gradle-wrapper.properties`）。
   `dl.google.com` 本身速度正常（约 9 MB/s），不用换。

### 版本号同步

`android/app/build.gradle` 顶部用 `JsonSlurper` 读根目录 `package.json`：

```groovy
def appPackageJson = new groovy.json.JsonSlurper().parse(file('../../package.json'))
def appVersionName = appPackageJson.version.toString()
// versionCode = major*10000 + minor*100 + patch
```

→ 网页端与安卓端版本号**永久同步**，不会再出现「网页 v1.11.0 / 安卓 1.0」。
**改 `package.json` 的 version 就够了，不用手动改 gradle。**

### ⚠️ 操作纪律

- **不要 `rm -rf` 工具链目录**：本机有安全删除护栏，超过 50 个文件会直接拦下
  （报 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`）。要重装就用 `unzip -o` 覆盖，
  或整目录改名后重新解压。
- **`sdkmanager` 别用 `| tail` 收尾**：命令实际早已结束，但管道不关闭，
  任务会一直挂着（踩过两次，白等 15 分钟）。**重定向到文件，再单独读日志。**
- **`unzip` 大包别放前台**：前台跑会被静默中断（JDK 那次只解出 `bin`/`conf`，
  `lib` 全丢，`java -version` 报 `could not open lib\jvm.cfg`）。
  用后台任务，跑完核对文件数（JDK 完整约 490 个文件）。

## 七、启动器图标（v1.12.0 修）

### 病根

`cap add android` 铺进去的是 **Capacitor 自己的默认图标**
（白底 + 蓝色电容符号 + Android Studio 的网格占位纹），

**`cap sync` 不会覆盖它们**，所以打出来的 APK 桌面图标和「周周记」毫无关系。

### 修法：`tools/make_android_icons.mjs`

源图用**已经生成好的 `web/icons/icon-512.png`**（不再重新解 3D 原稿），
借 puppeteer 的 canvas 解码 + 编码（Node 没有内置 PNG 编解码，而项目零依赖）。
输出三类：

| 产物 | 尺寸 | 用途 |
|---|---|---|
| `mipmap-*/ic_launcher.png` | 48/72/96/144/192 | 传统方形（Android 7.0/7.1） |
| `mipmap-*/ic_launcher_round.png` | 同上 | 传统圆形 |
| `mipmap-*/ic_launcher_foreground.png` | 108/162/216/324/432 | 自适应前景（Android 8+） |

### 🔴 自适应图标的两条硬知识

1. **画布 108dp，只有中央 72dp 保证可见**，外面 18dp 会被启动器遮罩裁掉。
2. **前景要放大到溢出自适应画布（scale 1.10），不要「缩进安全区 + 铺底色」。**
   试过「缩到 66.7% + 背景铺同色」：logo 自身的边缘（柔和渐变 + 浅色描边）
   和任何纯色/渐变背景都对不齐，圆角处必然留一圈能看见的接缝（已渲染预览确认）。
   放大到溢出后整幅画布**始终落在 logo 不透明的蓝底内**，根本没有「两种蓝相接」的地方。
   1.10 是算出来的：源图四周有 4% 透明留白，放大 10% 后留白被推出画布外
   （4% × 1.10 = 4.4% < 溢出量 5%）。

背景层是规范要求的必填层，平时看不见（前景已溢满画布），但**它并非无所谓**：
前景放大后四个**圆角**仍落在画布内，那几处是透明的，会露出背景。
所以背景用**与 logo 同向同跨度的 315° 线性渐变**（`<shape>` + `<gradient>`，
起止色从 `web/icons/icon-512.png` 实测取样），四角颜色才对得上。
纯色背景会让四角各差半个色阶，看起来像图标里套了个浅色方框（渲染预览确认过）。

用 `<shape>` 而不是 `<vector>`：只需要「起止两色、铺满整个 drawable」，
`<shape>` 完全够用，还少一层 aapt 编译风险。
同时另写一份 `values/ic_launcher_background.xml`（渐变中点的纯色）兜底，
供按名字找 `@color` 的工具/预览使用。

### 验证手段

图标没法直接看 —— 写个一次性脚本把「背景 + 前景」按 circle / squircle /
rounded / square 四种遮罩合成一张预览图再看。

## 八、设备端 OCR 与系统闹钟（v1.12.0）

### 🔴 APK 体积陷阱：Gradle 默认打包四种 CPU 架构

加入 ML Kit 后 APK **4.8 MB → 51.8 MB**。根因不是模型（模型才 6 MB），
而是 `libmlkit_google_ocr_pipeline.so` **单架构 11 MB（arm64）/ 6.6 MB（arm32）**，
而 Gradle **默认把 x86 / x86_64 / arm64-v8a / armeabi-v7a 四套全打进一个包**
→ 4 × 11 MB ≈ 40 MB 全是死重量。x86 两套只有**模拟器**用。

修法（`android/app/build.gradle` 的 `defaultConfig` 内）：

```groovy
ndk { abiFilters "arm64-v8a", "armeabi-v7a" }
```

→ **28.6 MB**。留 armeabi-v7a 是照顾少数 32 位老机型（多 6.6 MB）。
⚠️ 副作用：**装不进 x86 模拟器**（`INSTALL_FAILED_NO_MATCHING_ABIS`）。
要跑模拟器就临时注释掉这行或加回 `"x86_64"`。

体积拆解（28.6 MB）：lib 18 MB + dex 19 MB（multidex **13 个**，
四个语言识别器带来的死代码）+ 模型 6 MB + 网页 2 MB。

> 想瘦回去就删 `@capacitor-mlkit/text-recognition` 依赖 → ~5 MB，
> 代价是手机端图片识别退化为「请用粘贴文字」。
> 不值得为此手写精简插件：`.so` 是**所有语言共用**的一个 pipeline，
> 自己写也只能省下 dex 和 2.5 MB 模型，最多到 ~20 MB。

### OCR：插件只收文件路径，WebView 给的是 Blob

`ProcessImageOptions = { path, script }`，而 `<input type="file">` 给的是
**没有真实路径的 Blob**；`nativePromise` 又会 `JSON.stringify` 参数（`File` → `{}`）。
所以必须**先落盘**：

```
Filesystem.writeFile({ directory: 'CACHE', data: base64 })  →  { uri }
TextRecognition.processImage({ path: uri, script: 'CHINESE' })
Filesystem.deleteFile({ path, directory: 'CACHE' })          ← finally 里删
```

- `InputImage.fromFilePath()` 接受 `file://` / `content://` / 裸路径，
  Capacitor 给的是 `file:///data/user/0/<pkg>/cache/...`，可用。
- `CACHE` 目录**必定可写且不需要任何存储权限**，系统会自动回收。
- `DIR.CACHE` 是 v1.12.0 新加到 `native_bridge.js` 的（原来只有
  DOCUMENTS / DATA / EXTERNAL）。
- ML Kit 用的是 `com.google.mlkit:text-recognition-chinese`（**非 play-services 版**）
  → 模型**打进包**，真离线、不依赖 Google 服务。

### 通知图标：只取 alpha，且必须放 `drawable-*`

- **状态栏小图标**（`drawable/ic_stat_zhouzhouji.xml`）：
  🔴 Android **只取 alpha 通道**，颜色由系统重染。所以必须
  **白色剪影 + 透明底** —— 所有 `fillColor`/`strokeColor` 写 `#FFFFFFFF`，
  写别的颜色不报错但也没效果；**绝不能复用启动图标**（它有底，会变成白方块）。
- **通知大图标**（`drawable-*/ic_notification_large.png`，64dp）：
  🔴 **必须放 `drawable-*`，不能放 `mipmap-*`** ——
  插件用 `AssetUtil.getResourceID(ctx, name, "drawable")` 解析，只认 drawable 表；
  放 mipmap 解析不到，会**静默回退**成系统默认图标（灰色信息圆点），不报错。
- `capacitor.config.json` 里配 `plugins.LocalNotifications.{smallIcon, iconColor}`
  作为兜底（不传 per-notification `smallIcon` 时用它）。
- 🔴 **大图标缺失是「崩溃」不是「降级」**：`LocalNotification.resolveLargeIcon()`
  拿 `AssetUtil.getResourceID(...)` 的结果直接喂 `BitmapFactory.decodeResource()`。
  解析不到时返回的是 `RESOURCE_ID_ZERO_VALUE`（= 0），而 `decodeResource(res, 0)`
  **抛 `Resources.NotFoundException`** —— 整个通知构建炸掉。
  所以**只要传了 `largeIcon`，那个资源就必须真的存在**（5 个密度全都要）。
  小图标不会：`resolveSmallIcon()` 有 `if (resId == 0) resId = defaultIcon` 兜底。
- **已核对（v8.3.1 源码）**：`channelId` / `smallIcon` / `largeIcon` / `iconColor`
  都是 `LocalNotificationSchema` 的**合法 per-notification 字段**，
  解析顺序是「per-notification → 插件 config → 系统默认」；
  `channelId` 见 `LocalNotificationManager.kt:153`，图标见 `LocalNotification.kt:79-92`。
  （曾误以为 `channelId` 不在 schema 里 —— 是 `grep -A` 截断造成的错觉，别重犯。）

### 系统闹钟：必须增量对账，不能「全清全排」

`LocalNotifications` 的 `cancelAll()` 虽然会**保留已弹出的通知**（插件内部
用 `isCurrentlyTriggered` 判断，不会把它从通知栏抹掉），
但**每次全清全排会把已经响过的通知重新排一遍 → 重复响**。

所以 `reminder_service.js` 用一个本地账本
`localStorage['cw_reminders_scheduled'] = { 通知id: 签名 }` 做**增量对账**：

- **签名取「活动开始时间」，不是提醒时间。**
  这是关键 —— 取提醒时间的话，窗口内那条每次重算都会变，就会反复重排。
- 只在「新增 / 活动时间变了」时 `schedule`（同 id 会覆盖旧的）；
- 只在「活动删了 / 已开始 / 超出范围」时 `cancel`；
- 通知 id 直接用**活动的自增主键**（IndexedDB autoIncrement 本来就是正整数）。
  ⚠️ `Number('9')` 也是 9，所以数字字符串 id 是**故意放行**的
  （JSON 导入的旧数据友好），别当成 bug 去「修」。

其它口径：只在未来 **120 天**内登记，上限 **150** 条；
已经进入 30 分钟窗口的活动 → `at = now + 5s` 立刻响（签名仍取活动开始时间，
所以不会重复响）；`disable()` 是 **async**（要 await cancel），改它记得同步调用点。

### 合并清单要核对这几项

`cap sync` 后插件清单会自动并入，**必须核对**（用
`android/app/build/intermediates/merged_manifest/debug/.../AndroidManifest.xml`）：

- 权限：`POST_NOTIFICATIONS`（13+ 运行时权限）、`SCHEDULE_EXACT_ALARM`、
  `RECEIVE_BOOT_COMPLETED`、`WAKE_LOCK`
- 接收器：`TimedNotificationPublisher`（**真正触发闹钟的就是它**）、
  `NotificationDismissReceiver`、`LocalNotificationRestoreReceiver`（重启后恢复）
- 以及 `assets/capacitor.plugins.json` 里插件确实注册了

⚠️ 用 `grep "receiver\|provider"` 筛 `android:name` 会**漏掉
`TimedNotificationPublisher`**（它的名字里既没有 receiver 也没有 provider）。
要按 XML 标签名筛，别按字符串筛。

### 🔴 出包顺序：`cap sync` 绝不能和 Gradle 同时跑

踩过一次，**后果是静默出一个旧包**：

1. 一边跑 `gradlew assembleDebug`，一边跑 `cap sync android`；
2. `cap sync` 拷网页资源时被 Gradle 进程占住文件 →
   `removePluginsNativeFiles` 报 `universalify remove` 错误，**部分资源没拷过去**；
3. 紧接着再跑 `gradlew` → 因为资源没变，报 **`247 actionable tasks: 247 up-to-date`**，
   构建「成功」但 APK 里还是旧代码。

**所以必须串行**：`cap sync` 完全结束后再 `gradlew`。
而且**不能只看 BUILD SUCCESSFUL**，要核对任务数：
`27 executed` 这类才说明真的重新打包了；全 `up-to-date` 就要怀疑资源没同步。

最稳的校验是**直接翻包里的资源**：

```bash
unzip -p app-debug.apk assets/public/js/<改过的文件> | grep -c "<你刚加的字串>"
```

### 🔴 坑一：`signingConfigs` 必须写在 `buildTypes` 前面

Groovy DSL **顺序求值**。`buildTypes.release { signingConfig signingConfigs.release }`
在求值那一刻，`signingConfigs.release` 必须已经存在。
写在后面会报：

```
Could not get unknown property 'release' for SigningConfig container
```

### 🔴 坑二：`apksigner verify` 默认把 v1 报成 false（不代表缺失）

它按 **APK 自己的 minSdk** 来判该用哪些方案。本项目 minSdk 24，
而 API 24 起 v2 就够用 → v1 被标成「这个平台区间用不上」→ 打印 `false`。

**加 `--min-sdk-version 21` 才看得到 v1 的真实状态（true）。**

独立验证手段：包里 `META-INF/MANIFEST.MF` 的条目数应等于
「APK 总条目数 − 3」（三个 META-INF 文件自身不计入）。
本项目实测 638 = 641 − 3。

> ⚠️ 别被这个 `false` 骗去「修」一个根本不存在的签名问题 —— 我差点就去改。

### 为什么三种签名方案全开

minSdk 24 只要求 v2，AGP 默认也只出 v2。但**部分国产 ROM 的安装器和第三方
安装工具会查 v1**（JAR 签名），只出 v2 时偶发「解析包时出现问题」。
本机没有真机可验证，多签两种方案只是几秒钟的构建成本，
换掉一整类难排查的安装失败。`enableV1Signing/V2/V3Signing true`。

### debug 与 release 不能互相覆盖安装（**一次性，不是每次都这样**）

两者签名密钥不同 → 系统认为不是同一个应用 → 拒绝覆盖（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）。
**换签名必须卸载重装，而卸载会清空应用私有存储**（IndexedDB 就在里面）。
所以这一步只能在录入真实数据**之前**做一次。
（用户 2026-09-17 确认手机上还没录数据，所以直接换掉了。）

> 🔴 **用户 2026-09-22 追问：「为什么每次更新都必须卸载？」—— 答案是「不用，只有那一次」。**
> 需要卸载的唯一原因是**当时手机上装的是 debug 包**（`dist/debug历史/` 里的
> v1.11.0-debug / v1.12.0-debug），而新包是 release 签名，两者密钥不同。
> **从 v1.12.0 正式版起，所有 release 包用的是同一把钥匙**，
> 所以之后每次更新都是**直接覆盖安装**（Android 会显示「更新」而不是「安装」），
> **数据原样保留，不需要卸载**。
>
> 覆盖安装能被系统接受，靠三件事同时成立，缺一不可：
> | 条件 | 现状 |
> |---|---|
> | 包名相同 | `com.zhouzhouji.app`，从没改过 |
> | 签名相同 | 都用 `zhouzhouji-release.keystore` |
> | `versionCode` 递增 | `major*10000 + minor*100 + patch`，1.13.0 → 11300、1.13.1 → 11301 |
>
> ⚠️ **这把钥匙丢了 = 以后再也无法覆盖安装**（只能卸载重装，用户数据全没）。
> 所以 `D:\desktop\周周记-签名密钥备份\` 必须拷到项目外的地方。

### 卸载会丢什么、不丢什么

| 位置 | 卸载后 |
|---|---|
| IndexedDB（`campus_week_calendar`） | **删掉** —— 在应用私有目录里 |
| `localStorage` | **删掉** |
| `Documents/周周记备份/`（自动备份落点） | **保留** —— 公共目录，卸载不动它 |
| `ExternalStorage/…`（回退落点） | 删掉 —— 那是 `/sdcard/Android/data/<包名>/`，应用专属 |
| `Data/…`（最后回退） | 删掉 —— 应用私有目录 |

> 所以备份的落点很关键：**只有落在「文档」目录才扛得住卸载**。
> 目录回退链 `DOCUMENTS → EXTERNAL_STORAGE → DATA` 的后两级都活不过卸载，
> 设置页会把实际落点显示出来（`backup_dir_used`）。
> 真正可靠的「数据出手机」通道是 **设置 → 分享备份文件**（走系统分享面板存网盘/发给自己）。

### 重装后主动找回数据（v1.13.1）

用户原话：「卸载了我原来的数据不就没有了吗？能不能像其他软件一样搞一下更新自动替换」。

前面解释了「更新本来就不用卸载」，但**万一真的卸载了**（或换机、被系统清数据），
数据虽然还在「文档」目录里，却没人告诉用户。`offerRestoreIfFresh()` 补上这一步：

- **只在本机第一次打开时问一次**，标记用 `localStorage['cw_first_launch_done']`。
  🔴 **不能用 `kv` 存这个标记** —— `kv` 会被「设置 → 清空数据」一起清掉，
  那样用户刚清完数据、下次启动又会被问「要不要恢复你刚删的东西」。
- **本机已经有数据就不问**（正常覆盖更新走不到这里）。
  ⚠️ 判空要用 `DatabaseService.isEmpty()`，**不能用 `count()`** ——
  `count()` 只数 `events` 一张表，「只打过卡没记过活动」会被误判成空库，
  然后把提示弹给一个正在用的人。
- 翻三个候选目录找 `周周记-最新备份.json`，读到就用 `importJSON(json, {merge:false})` 整份还原。
- 浏览器里第一行就 `return null`（`isNative()` 为 false）。

回归在 `tools/verify_backup.mjs` 第 6.5 节（6 项）。

### `minifyEnabled` 为什么保持 false

Capacitor 插件是**反射加载**的（按 `capacitor.plugins.json` 里的类名
`Class.forName`），ML Kit 也大量用反射。开 R8 能砍掉不少体积
（19 MB 的 dex 里大部分是没用到的日/韩/梵文识别器），
但**没有真机验证过**，一旦被裁掉就是「装上就崩」。
要开请先加好 keep 规则并**在真机上完整跑一遍**。
