# 布局约定 · 编码纪律

## 一、布局约定（踩过坑）

- 纵向 flex 链：`#phone → #app → #screen-slot → .screen → .app-body`，
  每环都要 `display:flex; flex-direction:column; min-height:0`；
  滚动容器 `.app-body` 要 `flex:1; overflow-y:auto`。
- **`.screen` 是所有屏幕的根节点类，删掉它会让所有页面无法滚动。**
- **flex 子项默认 `min-height:auto`**，会按内容撑开 —— 要滚动就必须显式 `min-height:0`。
- **记录页子视图根节点必须带 `.app-body`**，否则拿不到 `flex:1` 与 `overflow-y:auto`，
  内容会被宿主 `overflow:hidden` 裁掉（`account_view.js` 就这么坏过，
  表现为「多账户只能看到第一个，滑不动」）。`.acct-view` 是特例，已单独补规则。
- **`scroll-behavior: smooth` 让程序化滚动变成异步动画**：
  `el.scrollTop = X` 后**立刻读 `scrollTop` 会拿到 0**，E2E 必须等动画跑完。
- **改布局后必须跑 E2E 第 12 组**（`getBoundingClientRect` 断言真在可视区）；
  E2E 第 8.9 组专门守账户页滚动。单元测试发现不了布局问题。

## 一之二、顶端留白与底部导航（v1.12.0）

### 顶端必须补 `env(safe-area-inset-top)`

`.app-header` 与 `.page-header` 的 `padding-top` 都写成
`calc(18px + env(safe-area-inset-top, 0px))`。
**安卓 15+（targetSdk 35 起）强制 edge-to-edge**，WebView 会一直画到状态栏下面，
不补这一段标题就贴着状态栏顶到屏幕上沿 —— 用户的原话是「顶端太满，没有空余」。

### 底部 dock：定宽 + 居中，且**不要**用 `left:50% + translateX(-50%)`

v1.12.0 之前 `.bottom-nav__item` 是 `flex: 1`，两项被顶到屏幕左右两端，
中间空一大片玻璃，用户嫌「隔得很远」。现在：

- `.bottom-nav`：`left:0; right:0; margin:0 auto; width:fit-content; max-width:calc(100% - 20px)`
- `.bottom-nav__item`：`flex: 0 0 auto; width: 92px`

两个坑：

1. 🔴 **`left:50% + transform:translateX(-50%)` 会让可用宽度只剩右半边**，
   shrink-to-fit 算出来只有 min-content，dock 会缩成一小坨（实测 142px）。
   必须用 `left:0; right:0; margin:0 auto; width:fit-content`。
2. 🔴 **`flex-basis` 撑不起 `fit-content` 的 dock** —— 容器按 flex 项**内容宽**
   （只有 21px 的图标）去算 max-content，同样缩成一坨。
   要给 `.bottom-nav__item` 显式 `width: 92px`。

效果对照（393px 视口）：两项中心距 **219px → 166px**，dock 从通栏 373px → 284px。

## 一之三、视觉层级：该大的大，该小的小（v1.13.1）

用户原话：**「你那个账户全部都是一样大？能不能该大大，该小小」**。

**根因不是「卡片一样大」，而是「每张卡里塞了同样多的东西」。**
当时资产板块的每个小格子都有三行 —— 标签 / 数值 / 一行解释文字
（「我欠别人的」「已拿回来的」…）。三行撑出来的高度让**格子比净资产大卡还高**，
整页自然就「什么都一样大」了。

所以这一条要和「少写解释性语句」一起修，它俩是同一个病：

| 层级 | 元素 | 做法 |
|---|---|---|
| 一级 | 净资产 | 字号 **34px / 800**、留白 18px、底色更实 —— 全页唯一的主角 |
| 二级 | 借入借出 / 定期 | **只有两行**（标签 + 数值），padding 6/10px、字号 15px、**行高 1.25** |
| 三级 | 账户概览 | **不用格子**，改成「标签在左、数值在右」的紧凑列表 |

**通用做法**：
- **用字号和留白拉层级，不要靠加边框/加底色** —— 加装饰只会让所有卡片更像。
- **同类信息堆成网格 = 没有层级**。四个等大的格子并排，眼睛找不到重点。
  次要信息改成列表（label 左 / value 右）就自然退到后面去了。
- **状态 ≠ 解释**。「1 笔逾期」是状态，值得占位置；「别人欠我的」是解释，删掉。
  状态可以压成**标签同一行的小角标**，不额外占高度。
- 层级要靠**断言钉住**，不能靠感觉。`verify_assets.mjs` 里写死了：
  净资产字号 ≥ 格子字号 × 1.8（实际 34 vs 17）、
  净资产卡高度 ≥ 格子卡高度、每格 `children.length === 2`、
  以及一份**禁用词表**（「别人欠我的」「已拿回来的」「累计口径」…出现即失败）。

> 🔴 **禁解释性文案，是用户明确提过的偏好**（2026-09-22）：
> 「不要有那么多解释性语句，像什么别人欠我的，已经拿回来的」。
> 以后写 UI 文案，**默认不解释「这个词是什么意思」** —— 标签本身该说清楚；
> 只在真的有状态/警告时才加字。同类改法：「按日均 ¥100 算，还能用 139 天」→
> 「日均 ¥100 · 还能用 139 天」（去掉「按…算」这种叙述腔）。

### v1.13.2：真正的高度是**行高**，不是 padding

上一轮改完用户仍说「还是很大」。实测单格 **56px**，比我按 padding 估的 43px 高一大截。

**默认 `line-height ≈ 1.6`** —— 15px 的字实际占 24px，是字号的 1.6 倍。
两行小字里，行高才是主要项，padding 只是零头。

| 组成 | 原 | 只减 padding | 再钉行高 |
|---|---|---|---|
| 上下内边距 | 20px | 12px | 12px |
| 标签行（10.5px × 行高） | ≈16.8 | ≈16.8 | **13.1** |
| 间距 | 3px | 2px | 2px |
| 数值行（15px × 行高） | ≈24 | ≈24 | **18.8** |
| 上下边框 | 2px | 2px | 2px |
| **单格高度** | **≈66px** | **56px** | **48px** |

> 🔴 **要收一个「两行小字」卡片的高度，先钉 `line-height`（1.25 左右），再动 padding。**
> 只减 padding 顶多收 20%。反过来，如果只钉行高不动 padding，也收不到极限 —— 两样都要。
> 已在 `.acct-metric__k` / `.acct-metric__v` / `.acct-metric__flag` 上显式写死行高，
> `verify_assets.mjs` 用 `单格高度 < 50px` 钉住（实际 48px）。

### v1.13.3：算「元素在滚动容器里的位置」不能用 `offsetTop`

用户 2026-09-22 报：「每次点击周历的时候，总是跳转到最后，周日，
而不是具体的当天日期居中」。

原来写的是：

```js
body.scrollTop = Math.max(0, sec.offsetTop - 12);   // ❌
```

`offsetTop` 量的是**相对 `offsetParent`** 的距离。而 `.app-body` 和 `.screen`
都**没有 `position`**，它们的 offsetParent 一路找到 `#app`（`#app` 才有 `position: relative`）。
于是量出来的是「相对整个应用顶部」的距离，比在滚动容器里的真实位置
**多出头部 + 筛选条 + 日期条那一整段**（实测 **205px**）。

多滚 205px 的后果分两种，都很糟：

| 内容高度 | 后果 |
|---|---|
| 够长 | 今天那一节被滚过头，停在**后一天** |
| 不够长 | `scrollTop` 被钳到最大值 → **直接落到周日**（用户报的就是这个） |

正确写法（不依赖 offsetParent，先拿两者相对滚动容器的位置，再居中）：

```js
const box = body.getBoundingClientRect();
const secBox = sec.getBoundingClientRect();
const topInBody = secBox.top - box.top + body.scrollTop;
const max = Math.max(0, body.scrollHeight - body.clientHeight);
const centered = topInBody - (body.clientHeight - secBox.height) / 2;
body.scrollTop = Math.max(0, Math.min(centered, max));   // ✅ 首尾由 clamp 兜住
```

> 🔴 **通用规则：`offsetTop` / `offsetLeft` 只在「元素和滚动容器共用同一个
> offsetParent」时才等于「元素在容器里的位置」。** 拿不准就用
> `getBoundingClientRect()` 相减 —— 它一定是对的。
> `scrollIntoView({ block: 'start' })` 也是安全的（浏览器自己知道滚动容器是谁），
> 但它**贴不了底/顶**：最后一节永远滚不到顶部，因为要它贴顶就得滚过 `maxScroll`。
> 写断言时要按这个物理事实分情况，别要求「点周日 → 周日贴顶」。

**断言钉在 `tools/verify_week_scroll.mjs`（19 项，`npm run verify:week`）**，
覆盖 5 个场景：内容够高 / 内容矮于视口 / 切到上一周不该滚 / 「回到本周」 /
点日期条跳转。断言的是**语义**（「今天那一节完整落在可视区内且尽量居中」），
不是「scrollTop 等于某个数」—— 后者一改布局就假红。

⚠️ **做过负向测试**：把实现临时还原成 `offsetTop` 版，脚本立刻报 5 项红
（`今天那一节完整可见（顶部没被切）（top=-193px）`、`内容不够滚时不乱跳（实际 22）`…），
改回来后恢复绿。**绿的前提是它真的能红。**



## 二、编码纪律（红线）

- 🔴 **一旦发现文件被对方删除/重组，立刻停手并报告，不要重建、不要争夺同一文件。**
  信号：① 文件 mtime 晚于自己最后一次编辑；② 自己刚写的文件突然消失；
  ③ 冒出自己没建过的新文件。此时只核对**核心资产**（`web/` / `tests/`）是否完好，然后就停。
- ⚠️ **发现「看不懂的改动」时，先查全项目引用面，再决定是「修正失配」还是「尊重变更」。**
  并发编辑下，一处版本号/名称与别处不一致，可能是**别人正在进行的升版**。
  方法：`grep -rn` 该版本号 / 新名称看是否成片出现 + 看文件 mtime。
  踩过：把 `settings_screen.js` 的 `v1.8.0` 误当误改改回 `v1.7.2`。
- **改完文件必须重新 Read/Grep 复核关键行，不能凭记忆做后续 Edit。**
- **语法排错三步**：① `node --check file.js` 拿首个报错行 → ② **直接读那个函数附近源码**
  → ③ 必要时才写辅助脚本。**括号数平衡 ≠ 语法正确**；**报错行往往是症状不是病灶**
  （报错在函数尾部时优先怀疑**最外层函数签名**，如漏 `async`）。
- **写断言前先读实现**（曾把 `stats.count` 当「活跃账户数」）。
- **检查脚本自身也会误报 —— 噪声多时先怀疑检查逻辑，别急着改被检查的对象。**
  踩过：PRECACHE 洁净度检查用 `/_/` 想匹配 `_zoom_icons.png`，结果把正常文件名里的
  下划线全匹配了，刷出 30 多条假阳性。**应锚定具体前缀**（`shot_` / `zoom_` / `mask_` / `debug`）。
- **写 CSS 前先核对 `:root` 令牌名**。凭印象写不存在的变量**不报错，只是样式静默失效**。
- **批量改文档不要用 bash 里嵌 `node -e`**，也别用 `cat <<EOF`（`${...}` 会被 shell 先吃一遍）。
  **一律用 Write / Edit 工具落盘。**
- **PowerShell `Set-Content -Encoding UTF8` 会写 BOM**，Python 的 `json.load` 直接报错 ——
  写 JSON 一律用 Write 工具。
- 🔴 **测试期望值反复调不收敛时，先怀疑模型而不是期望。**
  期望值改到第三次就该停下来，**先写独立真值表脚本钉死期望，再改实现**。
  踩过：让 `runCount` 兼任「补扣上限」，与 `lastRun` 语义重叠，来回震荡多轮。
- ⚠️ **`Edit` 报「String to replace not found」但 `Read` 明明一样时** ——
  把替换拆成两处更小的编辑通常就过了；**且 `old_string` 结尾不要带换行**，
  否则会把下一行的换行一起吃掉（踩过两次，把 `try {` 和函数声明粘连）。
- 🔴 **同一个文件的多处修改必须「一条消息一个 Edit」串行发。**
  在**一条消息里并行发多个 Edit 改同一个文件**，工具会各自报 `Successfully edited`，
  但实际只有一部分落盘 —— 另外几处**静默丢失**，`grep` 回去才发现原文没变。
  本会话踩了两次：`make_android_icons.mjs`（采样块与 return 没落盘）、
  `style.css`（`.app-header` 的 padding、`.bottom-nav` 的居中、`__item` 的定宽都没落盘，
  但工具全报成功）。
  **改完必须 `grep` 复核，不能凭「工具说成功」就往下走。**
