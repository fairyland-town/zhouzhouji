## 一、对账（核心功能）

用户诉求：**「不把自己的金额剩余多少全依靠给第三方平台，好明确知道自己的钱有没有
被误吞或者误扣而导致减少而没记录」**。本质是**对账**，不是「展示余额」。

| 口径 | getter | 语义 |
|---|---|---|
| 推导值 | `derivedBalance` | `opening + totalIn − totalOut` |
| 快照基准值 | `balance` | 最近快照 + 快照**之后**的流水 |
| 差额 | `balanceDiff` | `derivedFromOpeningAt(快照日) − (快照余额 + 快照后流水)` |

- **差额正负号有语义，不能取绝对值**：`> 0` → 平台扣得比记的多；
  `< 0` → 记的比平台扣的多；`|diff| < 0.005` → 对得上。
- **没设过基准的账户不显示推导数字**（`hasBaseline === false`），否则算出假数据。
- 流水按日期升序规范化：**0 元流水丢弃**、**负数额取绝对值**、**未知 `kind` 归为消费**。
- `dailyBurn()`/`daysLeft()` 无消费或余额为 0 时返回 `null`，**不除零**。
- 差额可「**补记**」成一笔流水调平，或「只留对账记录」。

## 二、账户 ↔ 记账的镜像关系（动这块要一起改）

**🔴 v1.9.0 起：只有「充值」进记账总账，消费不进。**

| 账户动作 | 记账结果 | 分类 id | source |
|---|---|---|---|
| 充值 | 收入 | `acct_in` | `account` |
| 消费 | **不镜像** | —— | —— |
| 对账差额补记 | 不镜像（消费方向） | —— | —— |
| 每月扣款 | 支出（不镜像）/ 收入（镜像） | `acct_in` | `recurring` |

- **v1.9.0 用户原话**：「避免重复计算，账户里面的消费不用走记账总账，
  只有充值的时候会记录在记账总账」。v1.7–v1.8 是充值消费都镜像，**已推翻**。
- 拦截点在 `flowToLedger()` 的**第一行**：`if (e.kind !== ACCOUNT_FLOW.IN) return null;`
  `_mirrorToLedger()` 拿到 null 直接返回。
- `acct_out` 分类**保留**（旧数据要能读出来），但**新代码不再产生它**。
  `purgeAcctLedgerMirrors()` 清历史镜像，靠 `kv` 键 `ledger_acct_mirror_purged_v109`
  保证只跑一次，在记账页与账户页的 `render()` 各叫一次。
- 记账页角标：「· 来自账户 · 充值」（`acct_in`）/「· 来自账户 · 每月扣款」（`recurring`）。
- `AccountService.addEntry` 用 `acc.addEntryWithId()` 拿新条目 id
  （`entries` 按日期升序，新条目不一定在末位，**不能靠 `entries.at(-1)`**）。

**五条约束**：

1. `acct_in`/`acct_out` 是**系统分类**（`system: true`），`ledgerCategoriesOf()` 会过滤掉。
   **绝不能出现在「记一笔」选择器里**，否则账会串。
2. `accountId` + `accountEntryId` 是**去重键**（`fromAccount` getter）：有则更新、无则新增。
3. **三处级联不能漏**：删流水 → `_unmirrorFromLedger` 清镜像（**要按 (accountId, entryId)
   清全部命中，不能只清第一条** —— 旧版可能同时留了 acct_out 与 acct_in）；
   删账户 → `removeWithLedger` 清全部镜像，确认框文案要写明这一点；删账户条目同理。
4. **记账页里镜像流水只读**：`openItemMenu` 判断 `e.fromAccount` 就弹说明抽屉。
5. **镜像失败不回滚账户流水**：账户余额是核心数据，附加写入失败只 `console.warn`。

## 三、每月定时扣款

`Account.recurring` =
`{ enabled, day, amount, note, kind, since, lastRun, runCount, sinceSkip }`。

**🔴 v1.9.0 时序规则（用户明确要求，别再改回去）** —— 「不是设置了立即扣除，
而是在固定的设置的那一天扣款」。

| 设置那天 | 本月扣不扣 | 什么时候扣 |
|---|---|---|
| **早于**扣款日 | 扣 | 本月那天 |
| **等于**扣款日 | 扣 | 当天 |
| **晚于**扣款日 | **不扣** | 下月那天 |

- **设置当时永远不扣款。**
- **错过的月份全部补上，不设上限**（用户确认：「房租本来就是要交的」）。
- 只有**改金额**才把期数重置回第 1 期；改日期/备注不动 `since`/`lastRun`。

**字段职责（别再让两个变量描述同一件事）**：

| 字段 | 职责 |
|---|---|
| **`lastRun`** | **唯一权威** —— 已执行到哪月。`dueRecurring` 起点 = `lastRun + 1` |
| `since` | 只负责「不许倒扣启用前的月份」，**重设时原地保留** |
| `sinceSkip` | 启用月那期是否已放弃（设置日已过扣款日 → `true`） |
| `runCount` | **不参与任何判定**，仅供「第 N 期 / 共 M 期」展示 |

**判定逻辑（保持这么短）**：

```js
let from = r.lastRun ? addMonths(r.lastRun, 1) : (r.since || curMonth);
if (r.since && from < r.since) from = r.since;
if (from > curMonth) return [];
// 逐月扫到本月，到日子才收，sinceSkip 那期跳过
```

> ⚠️ **起点必须优先取 `lastRun + 1`，不能是 `curMonth`** ——
> 否则只有 `lastRun` 的老账户会把中间跨的月份整段跳过。

**其它**：

- **`day` 限制 1–28**：29–31 在有的月份不存在，允许填就必须定义「2 月怎么算」。
- **`amount > 0` 才算真正启用**（`hasRecurring`）—— `enabled: true` 但金额 0 时 UI
  不显示任何扣款承诺。
- **关闭时要同时清掉 `lastRun` / `since` / `runCount` / `sinceSkip`**，否则重开不立即生效。
- **旧数据兜底**：`normalizeRecurring()` 对 `null` / 非对象 / 缺字段全部回落「未启用」。
  改它之后必须重跑 `tests/account_test.mjs` 的旧记录用例。
- `dueRecurring()` 是**纯函数**（可测）；`runDueRecurring()` 才落库，在
  `account_view.render()` 最前面调用（PWA 会被系统杀后台，没有后台定时器）。
- ⚠️ `runDueRecurring` 必须记 `created` 流水的 **id** 去镜像，不能用「日期相同」反查
  —— 会把用户当天手记的流水也标成 `source:'recurring'`。

## 四、资产板块（净资产 / 借入借出 / 报销 / 黄金 / 定期）—— v1.13.0

账户页顶部新增「资产总览」板块（参考「随手记」资产账户页）：
净资产大卡 + 两排指标格子 + 全局口径格子 + 按类型分组的账户分布。

**存储：全部放已有的 `kv` 表，不新建 store。**

```js
export const ASSET_KEYS = {
  LOANS: 'cw_loans', REIMBURSEMENTS: 'cw_reimbursements',
  GOLD: 'cw_gold', GOLD_PRICE: 'cw_gold_price', DEPOSITS: 'cw_deposits',
};
export const LOAN_DIRECTION = { IN: 'in', OUT: 'out' };  // IN=我欠别人(负债) OUT=别人欠我(资产)
export const DUE_SOON_DAYS = 30;
```

> 🔴 **为什么用 `kv` 而不是新建 store**：新建 store 要升 `DB_VERSION`、写迁移、
> 改备份顺序、改清空分类 —— 四处联动只为存几个数组，不值。
> `kv` 本来就在 `BACKUP_STORES` 里，白拿备份能力。
> 代价是**清空分类必须显式列 `kvKeys`**（见 `CLEAR_CATEGORIES`）。

**净资产口径**（`summarizeAssets`，纯函数，`today` 由外部注入）：

```js
const totalAssets      = round2(cashPositive + lentOut + pendingTotal + goldValue);
const totalLiabilities = round2(cashNegative + borrowedIn);
const netWorth         = round2(totalAssets - totalLiabilities);
```

- **借入是负债、借出是资产** —— 不是「都是钱」。
- **定期存款不计入净资产**：那笔钱通常已躺在某个账户余额里，再加一次就是重复计算。
  用户选的就是「全局口径」，要避免的正是这个。
- 余额为负时按 `max(bal,0)` / `max(-bal,0)` 拆正负两侧，不会出现负数资产。
- `daysBetween()` 用本地时区解析 `YYYY-MM-DD`（`new Date('YYYY-MM-DD')` 按 UTC 解析，会差一天）。
- 逾期按方向拆：`overdueInCount/outCount` + 对应金额。
  ⚠️ **只给一个合计的 `overdueCount` 会让唯一的逾期借入把「借出」也标成「1 笔已到期」**。

**UI 约定**（`screens/record/account_view.js`）：

- `money()` 带千分位，负数输出 `-¥1,234.50`。
- `toneWhen(n, tone)`：`|n| < 0.005` 时**不给颜色**。
  ⚠️ 「借入 ¥0.00」染红、「借出 ¥0.00」染绿 = **数字对但颜色在撒谎**，读起来像出了问题。
- 金额隐藏开关用 **`localStorage`（`cw_hide_amounts`）而不是 IndexedDB** ——
  `render()` 是同步的，异步读会让真实数字**先闪一下**再被遮住。
- `[data-field]` 要标在**数值的 `<span>`** 上，不要标在整张卡片上 ——
  否则回归脚本读到的文本是「借入¥300.001 笔已到期」。
- 保留了 `[data-field="total-balance"]` 与 `.acct-total__add` 供旧回归脚本使用。

**`DatabaseService` 的三个坑**：

1. 🔴 `_remove(store, id)` 内部是 `store.delete(Number(id))` —— 对 autoIncrement 表正确，
   但对 `kv`（`keyPath: 'key'` 是**字符串**）会得到 `Number('cw_loans')` = `NaN` →
   `DataError: The parameter is not a valid key`。**清 `kv` 一律用 `removeSetting(key)`**。
2. `countCategory()` 对 kv **只统计 `Array` 的长度**（标量计 0）——
   把「一个金价」说成「1 条记录」会让清空提示的数字莫名其妙。
3. `clearCategory()` 要遍历 `kvKeys` 调 `removeSetting`。

## 五、充值「关联账户」= 转账（v1.13.5，用户 2026-09-23 第 3 条）

入口：账户页给 A「充值」→ 第二步（「这笔钱的来源」）多一行 `关联账户`。
用户确认的口径是 **「转账：从那个账户真扣钱」**，不是只做个标记。

`AccountService.transfer({ fromId, toId, amount, date, note })`：

| 侧 | kind | 金额 | 备注 | 额外 |
|---|---|---|---|---|
| `to`（转入） | `in` | +n | 用户填的来源 | `linkedAccountId = from.id` |
| `from`（转出） | `out` | −n | `转给「A」` | `linkedAccountId = to.id` |

然后两条互相指认：`inEntry.linkedEntryId = outEntry.id; outEntry.linkedEntryId = inEntry.id;`

🔴 **必须在 `update()` 之前赋值** —— `update()` 会把 `entries` 序列化落库，
之后再改就只改到内存里那份。

🔴 **只镜像转入侧**：`await this._mirrorToLedger(to, inEntry, { source:'account' })`，
**不要**再镜像 `outEntry`。镜像两条的话记账页当月收入会翻倍（v1.9.0 修过的老毛病）。
`flowToLedger()` 对 `ACCOUNT_FLOW.OUT` 返回 `null`，是第二道保险。

⚠️ 但正因为有**两道**保险，测试里「当月收入不是 400」这条断言
单独拆任何一道都还是绿的 —— 见 MEMORY.md 红线 38，
必须另有一条**只经过 `flowToLedger`** 的用例（账户消费）才钉得住。

🔴 **删除要级联**：`removeEntry()` 先把 `linkedAccountId` / `linkedEntryId`
读下来（删完就查不到了），删自己 → 撤自己的镜像 → 再撤对方那条 + 对方的镜像。
只删一半会留下「钱从 A 出去了、但 B 没收到」的半截账，
两个账户各自看都「算得通」，只有放一起看才发现少了 n。

约束与边界：
- 只能选**别的**账户（`Number(fromId) !== Number(toId)`），转给自己会把余额算成两倍。
- 归档账户不列进选项（它们已经「不参与」了，不该再往外转钱）。
- 消费（`ACCOUNT_FLOW.OUT` 方向的那次操作）**没有**这一行 —— 消费的关联入口在记账页。
- `normalizeEntry()` 是字段白名单，`linkedAccountId` / `linkedEntryId` 必须列进去，
  否则 save→reload 一轮就静默消失。

UI：`promptDialogEx`（`checkin_view.js`）的 `extra` 参数渲染 `.field-pick` 行，
**放在输入框上面**（用户原话「上面多加一个关联账户的选项」）。
`promptDialog` 是它的薄包装，**返回形状不能动**（30+ 个调用点在用）。

### 🔴 关联账户是**必选**的（v1.13.5 第二轮，用户 2026-09-23 第 2 条）

用户原话：「账户充值的时候，那个关联选项改成必选项」。

关键是把「**调用方没传初始值**」和「**用户还没选**」区分开：

```js
let extraValue = extra ? ('value' in extra ? extra.value : undefined) : null;
```

- `'value' in extra` 为假 ⇒ 调用方没给初始值 ⇒ `undefined` = **未选**
- `'value' in extra` 为真 ⇒ 调用方给了哨兵 ⇒ 已经是「已选」状态

账户页调用时**故意不传 `value`**，于是初始就是 `undefined`；
占位文案从「不关联（钱来自账户之外）」改成「**请选择**」，
行本身加 `.field-pick--todo`（虚线边 + 主色底）明示「这里还没填」。
再配 `extraRequired: isIn && others.length > 0`（充值 + 有别的账户才要求）。

🔴 **拦截必须在弹窗内部就地做**（hint + 行抖动 700ms），
**不能让调用方 `return`** —— 那是「点了保存没反应」，用户更懵（MEMORY.md 红线 25）。

🔴 **选项值不能用 `null`** —— `actionSheet` 用 `null` 表示「取消」，
传进来会被当成取消路径。所以「不关联」用哨兵 **`'__none'`**。

⚠️ `paintExtra()` 要**在 `extraRow` 建好之后**再调，否则第一次绘制时
根本没有行可以去 toggle `--todo`。

测试：`tools/verify_account_transfer.mjs`（**64 项**，`npm run verify:transfer`），
7 组：选择行 / 钱真动了+互相指认+只镜像一条 / 「不关联」不碰别人 /
账户消费不进总账 / 删除级联 / **关联账户必选** / 控制台。
新增断言：默认是「请选择」不是「不关联」／行带 todo 样式／
不选就保存被就地拦下（有「请选…」hint 且行仍是 todo 态）。

⚠️ **顺序坑**：第二步的「来源」备注是 `required`，它的校验排在选择器前面 ——
所以要先 `typeInModal()` 填好备注，才能测到选择器的拦截；
测完再清掉备注去测备注自己的拦截。

⚠️ 该脚本进账户页后必须先 `expandDetail()` —— 「账户明细」默认收起时
`.acct-card` **压根不渲染**；卡片按钮用 `data-action="recharge"/"spend"/"all-flows"` 定位。

## 六、账户之间的转账**不计入收入**（v1.13.7，用户 2026-09-24）

用户原话：「账户与账户之间的转账不计入收入，因为，在钱入账的时候已经计算过了的」。

### 为什么

钱只是在自己名下的两张卡之间挪，**总资产分文未变**。那笔钱**首次充值进来**时
记账页已经算过一次收入了，转账再算一次就是同一笔钱算两遍 ——
跟 v1.9.0 要消灭的「账户消费镜像」是同一类错误。

### 判据：`linkedAccountId`

账户流水的 `linkedAccountId` **只有 `transfer()` 会写**（见 `models/account.js`
的 `addEntryWithId` / `normalizeEntry`）。外部充值（`recharge` → `addEntry`）
和每月扣款（`runDueRecurring`）都不写。所以：

```js
// account_service.js flowToLedger()
if (e.kind !== ACCOUNT_FLOW.IN) return null;                 // v1.9.0：只有充值进总账
if (e.linkedAccountId != null) return null;                  // v1.13.7：转账不进总账
```

⚠️ `transfer()` 里那行 `_mirrorToLedger(to, inEntry)` **保留**着 ——
它现在必然返回 null，留着是为了让「所有镜像都走同一个门」，别在别处另开一条路。

### 🔴 旧数据也要清：`purgeTransferLedgerMirrors()`

v1.13.5 加「关联账户 = 转账」时，转入侧还是照充值的老路子镜像进了总账。
**只拦新的不够** —— 那些已经写进库里的镜像会把用户的收入总额一直顶高，
而且他自己翻账单看不出哪一笔是错的。

- kv 标记 `ledger_transfer_mirror_purged_v1137`，**只跑一次**；
- 在 `ledger_view.js` 与 `account_view.js` 各调一次（与 `purgeAcctLedgerMirrors` 并列）；
- 判定链路：记账镜像身上带 `accountId` + `accountEntryId` → 顺着去账户里找那条流水
  → 它有 `linkedAccountId` 就说明是转账的一半。

⚠️ **不能只看 `category === 'acct_in'`**：外部充值镜像也是这个分类，
那是用户**要**的，删了就把收入删没了。所以必须回查账户流水。

⚠️ **只删记账侧，绝不碰账户流水** —— 转账那两条是余额的事实依据，
删了两个账户的余额会同时对不上。
**别走 `unlinkLedgerEverywhere`**：那个的语义是「撤挂账」，会把账户流水一起删掉。

### 验证（`npm run verify:transfer`，64 → **90 项**）

- 第 2 组：转账 200 后 → 记账总账 **0 条**、当月收入 **0**（原来断言的是 1 条 / 200）；
- 第 3 组（**反向对照**）：选「不关联」的外部充值 50 → 总账 **1 条**、当月收入 **50**。
  ⚠️ 这一组不能省：如果「转账不进总账」是靠「把 `acct_in` 全删掉」实现的，
  第 2 组照样绿，但用户真正要的收入也没了。
- 第 6 组：塞一条**假的转账镜像**（999）+ 一条**真的外部充值镜像**（77），
  清掉 kv 标记重进记账页 → 999 被清、77 留着、当月收入 127、
  **账户流水一条没少**、余额不受影响、再进一次不再动（幂等）。
- 第 7 组：**账户概览的合计**（见下面第七节）—— 先证明转账真的发生了
  （两边余额各动 400），再看合计纹丝不动。

负向验证（改坏 → 确认变红 → 改回）：

| 改坏的地方 | 结果 |
|---|---|
| 拆掉 `flowToLedger` 里的 `linkedAccountId` 守卫 | **5 条红**（总账 1 条≠0、当月收入 200≠0…） |
| 让 `purgeTransferLedgerMirrors` 直接返回（假装跑过） | **4 条红**（999 没清、当月收入 1126≠127） |
| `summarizeOverview` 改回直接读 `totalIn` / `totalOut` | **4 条红**（概览显示 ¥1,526.00 而不是 ¥127.00） |
| `isTransferLeg()` 恒返回 false | 单元 **8 条红** + 浏览器 **6 条红**（模型层 2 + UI 层 4） |

## 七、账户概览的「累计充值 / 累计消耗」也不含转账（v1.13.7 续，2026-09-24）

第六节只修了**记账总账**；账户页顶部那个「账户概览」是**另一套代码**，
同样被转账顶高，一并修了。

### 为什么两个数字不能共用

| 口径 | 数字 | 对不对 |
|---|---|---|
| 单个账户卡片「累计充值」 | `a.totalIn` | ✅ **对**。「这张卡进过多少钱」—— B 转 200 给 A，A 确实进过 |
| 账户概览「累计充值」 | Σ 各账户 `totalIn` | ❌ **错**。A +200、B 的 `totalOut` +200，可钱没离开过这个人 |

**用户问「这张卡进过多少钱」时 `totalIn` 是对的；一旦把几个账户相加，它就是错的。**
这不是「哪个字段写错了」，是**同一个字段在两种问法下的答案不同**。

### 做法

`models/account.js` 新增一对 getter（不动原来的 `totalIn` / `totalOut`）：

```js
export function isTransferLeg(e) {          // 判据同第六节：只有 transfer() 写这个字段
  return !!e && e.linkedAccountId !== null && e.linkedAccountId !== undefined;
}
get totalInExternal()  { return round2(entries.filter(e => e.kind === IN  && !isTransferLeg(e)).reduce(...)); }
get totalOutExternal() { return round2(entries.filter(e => e.kind === OUT && !isTransferLeg(e)).reduce(...)); }
```

`models/asset.js` 的 `summarizeOverview()` 改成优先取 `*External`：

```js
const amountOf = (a, externalKey, plainKey) =>
  a[externalKey] !== undefined ? a[externalKey] : a[plainKey];
```

⚠️ 那个 `?? 退回` **不是可有可无的**：`tests/asset_test.mjs` 的夹具是**普通对象**
（只有 `totalIn` / `totalOut`，没有 `entries`），不退回就会算成 0。
**但也要注意**：这是「两种输入形态」的分支，写测试时必须两条路径都钉住
（`asset_test.mjs` 里各加了一条）。

### 验证（`verify:transfer` 第 7 组，16 项）

先真做一笔转账（微信零钱 → 一食堂饭卡 400），再断言：

```
✓ 🔴 转入方 totalIn 涨到 1526（流水确实落了）      ← 没有这条，下面那条会被"转账失败"白白满足
✓ 🔴 但 totalInExternal 仍是 127（转账不算充值）
✓ 🔴 概览「累计充值」没变（转账不是充值）
✓ 🔴 概览「累计充值」= ¥127.00（50 + 77 两笔外部充值）
✓ ⚠️ 卡片「累计充值」仍是 ¥1,526.00（"这张卡进过多少" 是对的，不跟着改）
```

🔴 **「证明转账真的发生了」那两条是必需的**：只断言「合计没变」的话，
一个静默失败的转账也能让它变绿 —— 等于什么都没测。

⚠️ 最后那条**故意钉住「不改」**，防止后来者"顺手统一"把单账户口径也扣掉转账。

### 排查结论：全站只有这两处

`grep totalIn` 全 `web/` 只有 4 个落点：`asset.js` 的 `summarizeOverview`
（已修）、`account_view.js` 的概览格子（已修）与卡片格子（**故意不改**）。

净资产 / 资产分布 / `stats.totalBalance` **不受影响** —— 它们算的是**余额快照**，
转账只是在两个自己的账户之间挪，合计天然不变。**只有「流量类」的累计值才会双计。**

## 八、`dailyBurn()` 也不把转账当消费（v1.13.7 续，2026-09-24 已改）

**（2026-09-24 排查时发现，验证后由用户拍板「改」）**

`models/account.js` 的 `dailyBurn()` 原本用的是 `this.totalOut`，
区间也取到最早那笔 OUT。于是**转出方**那张卡的「日均消耗 / 还能用多久」被一笔转账顶飞。
实测（真跑模型）：

```
零钱：期初 500，今天转出 400 给饭卡（linkedAccountId 有值）
余额 100 / totalOut 400 / totalOutExternal 0
→ 日均消耗 400 → 还能用 0 天     🔴 卡里明明还有 100
```

而且 `daysLeft() <= 7` 会点亮 `.acct-bal__pace--warn`（警告色），
即**一个纯转账触发「余额快告急」的假警报**。

### 修法

```js
const outs = this.entries.filter((e) => e.kind === ACCOUNT_FLOW.OUT && !isTransferLeg(e));
...
return round2(this.totalOutExternal / spanDays);
```

🔴 **求和与区间必须用同一套过滤。** 只把 `totalOut` 换成 `totalOutExternal`、
而 `outs` 里还留着转账的话，会算出「20 / 31 ≈ 0.65」这种**被拉长的分母** ——
数字看着更温和，其实是错的。负向验证专门测了这个「只修一半」：
单元测试立刻 **2 条红**（`混合场景日均 = 20 / 4 天 = 5`）。

改完行为：只有转账的账户 `daysLeft()` 返回 null → UI 里那行
`日均 … · 还能用 …` **整条不渲染**（`account_view.js` 的 `acct-bal__foot`）。
这是**用户看得见的行为变化**，所以当初没有顺手改、先问了一句。

### ⚠️ 顺带纠正一条假注释

原注释写着「按「有消费记录的天数区间」估算，**最多看最近 90 天**」，
但代码里**从来没有这个上限**（`outs[0].date` 一直取到最早那笔）。
已把注释改成与实现一致。
**要不要真加 90 天上限是另一个决定**，别顺手加（会让老账户的日均变大、可用天数变短）。

### 回归

- 单元 `account_test.mjs` 第 6 组 +7 项（182 → **189**）：
  纯转账 → 日均 0 / 天数 null；混合（转账在 30 天前、消费在 3 天前）→ 日均 5 / 天数 16。
  ⚠️ 混合那组**同时钉住求和与区间**，是专门为「只修一半」设计的。
- 浏览器 `verify:transfer` 第 7 组 +2 项（90 → **92**）：
  `🔴 转出方（微信零钱）不显示「日均 / 还能用」` +
  **对照组**「有真实消费的饭卡仍显示」（否则「把预估整个删掉」也能让上一条变绿）。

负向验证：

| 改坏的地方 | 结果 |
|---|---|
| 整段还原成旧实现 | 单元 **4 条红** + 浏览器 **1 条红** |
| **只换求和、不换区间**（只修一半） | 单元 **2 条红** |
